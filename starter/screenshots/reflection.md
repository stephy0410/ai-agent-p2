During the project Customer Support Agent, one of the most interesting integrations was adding Pydantic for the calculate_loyalty_discount tool. I wanted to challenge myself by implementing pydantic, so I opted to intercept and validate the JSON generated by the Code Interpreter against a strict Pydantic model (DiscountBreakdown) before passing it back to the LLM. This guarantees that the agent receives exactly the expected fields (such as `tier_discount` and `points_redeemed`) with the correct data types, catching any malformed responses early and guaranteeing the tool is truly production-ready.

Throughout the project, and from what I have learned in my job, the most complex technical challenge is always related to managing cloud permissions and roles (IAM). During testing of the Knowledge Base (RAG) and the Web Browser tool (`AgentCoreBrowser`), the agent would fail or refuse to execute actions. Upon investigating the logs, I discovered that the execution role auto-generated by the Bedrock environment lacked critical permissions (`bedrock:Retrieve` and `bedrock-agentcore:StartBrowserSession`). To resolve this, I designed a custom JSON policy document (`kb-policy.json`) and used the AWS CLI (`aws iam put-role-policy`) to inject these permissions directly into the agent's role, instantly unlocking its capabilities.

When considering moving this agent to a production environment, security, specifically the concept of least privilege,becomes an essential factor. While broad permissions (e.g., `bedrock-agentcore:*`) might be assigned during development to resolve blockers, doing so in production poses a serious risk; the IAM role must be strictly limited to the specific ARNs of authorized tools to prevent vulnerabilities should the model hallucinate instructions. Furthermore, regarding scalability, my tests revealed that multiple interactions using the same ID can saturate memory and obscure key memories due to the `top_k` limit. For example, when I had issues with one test, since k was 5 if I modified a failed test, when trying again, it resulted in insufficient memory. In a production environment, it will be crucial to implement retention policies or memory compression routines to avoid infinite storage growth, maintain fast query performance, and control AWS costs.
