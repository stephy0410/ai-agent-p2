## MY REFLECTION 

During the development of this Customer Support Agent, one of the most interesting integrations was the implementation of a long-term memory system using the `MemoryHook` class. As a design choice, I opted to retrieve memories via semantic search (`retrieve_memories` with `top_k=5`) and inject them directly at the beginning of the user message under the "Customer Context" tag. This architectural decision was pivotal because it grants the foundational model (LLM) immediate access to customer history—such as names and preferences—without requiring additional tool-calling iterations, thereby significantly reducing latency for each interaction.

Throughout the project, and from what I have learned in my job, the most complex technical challenge is always related to managing cloud permissions and roles (IAM). During testing of the Knowledge Base (RAG) and the Web Browser tool (`AgentCoreBrowser`), the agent would fail or refuse to execute actions. Upon investigating the logs, I discovered that the execution role auto-generated by the Bedrock environment lacked critical permissions (`bedrock:Retrieve` and `bedrock-agentcore:StartBrowserSession`). To resolve this, I designed a custom JSON policy document (`kb-policy.json`) and used the AWS CLI (`aws iam put-role-policy`) to inject these permissions directly into the agent's role, instantly unlocking its capabilities.

When considering moving this agent to a production environment, security—specifically the principle of least privilege—becomes a critical factor. While broad permissions (e.g., `bedrock-agentcore:*`) might be assigned during development to resolve blockers, doing so in production poses a serious risk; the IAM role must be strictly limited to the specific ARNs of authorized tools to prevent vulnerabilities should the model hallucinate instructions. Furthermore, regarding scalability, my tests revealed that multiple interactions using the same ID can saturate memory and obscure key memories due to the `top_k` limit.For example, when I had issues in one test, since the k was equal to 5 when I modified the failed test, after trying again to test it, the memory was insufficient. In a production environment, it will be crucial to implement retention policies or memory compression routines to avoid infinite storage growth, maintain fast query performance, and control AWS costs.
